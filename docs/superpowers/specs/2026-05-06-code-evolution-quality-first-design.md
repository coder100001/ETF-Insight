## 1. 背景与动机

### 1.1 为什么需要这个分析？

ETF-Insight 经过 v2.4 → v2.10 的快速功能迭代，已从单一的 ETF 查看工具演变为具备量化分析、AI Agent、多微服务架构的复杂系统。在继续扩张之前，需要系统性评估代码健康度，确定下一步最优路径。

### 1.2 当前项目状态快照

| 维度 | 版本 | 状态 | 关键指标 |
|------|------|------|----------|
| 架构 | v2.10 | Go 单体 + 3 个 Python 微服务（Agent/Data/Analytics） | 混合架构 |
| 功能 | v2.10 | 量化分析、AI Agent、数据服务、回测引擎 | 功能丰富 |
| 测试 | — | 整体 ~55%，核心算法较高，前端 0% | 需提升 |
| 文档 | v2.9 | agents.md、DOCUMENT_INDEX.md、路线图 | 较完善 |
| 质量 | — | pre-commit 钩子完整、JSONMap 类型安全重构完成 | 改进中 |

### 1.3 业务/技术驱动因素

- **技术债务累积**: 快速迭代导致测试覆盖不足、双实现并存
- **微服务化加速**: Phase 2-4 连续提取 Python 服务，运维复杂度增长
- **生产就绪需求**: 从开发工具向生产级平台过渡的质量门槛

## 3. 演进方案对比

### 方案 A：继续微服务提取路径（当前轨迹）

沿用已验证的模式——持续从 FinceptTerminal 提取 Python 模块，封装为独立 FastAPI 微服务。

**优点**: 已有成功模式（3个Phase验证）、快速扩展功能、各服务独立部署
**缺点**: 运维复杂度线性增长、服务间调试困难、AGPL 许可证传染风险
**适合场景**: 追求功能丰富度、团队有微服务运维经验

### 方案 B：质量优先 — 稳固基础再扩张 ✅ **推荐**

暂停新服务提取，聚焦现有代码的质量提升。分 P0-P3 四层递进。

**优点**: 降低技术债务、提升可维护性、为后续扩张打牢地基
**缺点**: 短期内无新功能产出、需要团队文化转变
**适合场景**: 准备进入生产环境、长期维护性优先

### 方案 C：平台化演进 — 开源金融分析基础设施

将定位升级为"开源量化金融基础设施平台"，引入插件系统、策略市场、API 开放。

**优点**: 最大商业/学术价值、社区驱动的可持续性、差异化竞争壁垒
**缺点**: 周期长（12-18个月）、需要社区运营投入、架构复杂度最高
**适合场景**: 长期战略布局、有资源投入生态建设

### 方案 D：质量 + 功能并进

B+A 组合：先花 2-4 周提升核心质量（P0 测试），然后继续微服务提取路径。

**决策结果**: 选择 **方案 B（质量优先）**，原因：
1. 当前测试覆盖率 ~55% 是最大的工程风险
2. 存在两套 BL 实现并存的架构问题需先解决
3. 质量地基打好后，方案 A 或 C 的执行效率会大幅提升

## 4. 详细设计：质量优先策略

### 4.1 分层路线图

#### P0: 核心算法安全网（第1-2周）

目标：核心计算逻辑零回归风险

| 模块 | 当前覆盖率 | 目标 | 关键动作 |
|------|-----------|------|----------|
| `services/optimization/` | 部分（MPT/BL/RP 有测试） | 100% | 补充边界测试：空输入、极端权重、退化矩阵 |
| `services/factor/` | 80.8% | 95%+ | Fama-French 五因子边界、Tikhonov 正则化验证 |
| `services/risk_models/` | 100%（声称） | 100%+ 验证 | VaR/CVaR 参数法 vs 历史法一致性交叉验证 |
| `models/black_litterman.go` | 通过 handler test 间接覆盖 | 直接单元测试 | JSONMap 序列化/反序列化、nil 处理、格式兼容 |

#### P1: 服务层集成测试（第3-4周）

目标：业务流程端到端可信

| 服务 | 测试范围 | 关键场景 |
|------|----------|----------|
| `alpha_view_service` | CRUD + BL 闭环 | 因子信号→Alpha观点→BL后验收益 完整链路 |
| `portfolio_optimizer` | MPT/BL/RP 三种优化 | 有效前沿生成、约束满足、权重归一化 |
| `exchange_rate` | 多数据源故障转移 | 主源挂掉→自动切换→恢复→切回 |
| `report_service` | 报告生成完整性 | 数据填充、模板渲染、格式正确性 |

#### P2: Handler/API 层测试（第5-6周）

目标：接口契约可靠

- 所有 Handler 核心 HTTP 端点测试（请求验证、响应格式、错误码）
- 中间件链路集成测试（审计→验证→限流→Handler）
- 错误响应格式 `{ success, error, error_code }` 一致性验证

#### P3: 基础设施（第7-8周+）

目标：可持续的质量保障体系

- 性能基准测试套件（k6/hey）：API P95 < 200ms
- CI 覆盖率门禁：<80% 无法合并到 main
- 运行时监控 + 告警（Prometheus + Grafana 或轻量替代）

### 4.2 TDD 强制流程

Phase 4 Analytics Service 已成功采用 RED→GREEN→REFACTOR 模式，推广到全项目：

```
Iron Rule: 没有失败的测试，不允许写任何生产代码

RED   → 编写失败测试，描述期望行为
GREEN → 写最少代码使测试通过
REFACTOR → 清理代码，保持测试绿灯
循环 → 直到功能完整且代码整洁
```

### 4.3 技术债务修复清单

| # | 债务项 | 严重程度 | 修复方案 | 所属阶段 |
|---|--------|----------|----------|----------|
| D1 | `alpha_view_service_test.go` 使用旧 `string` 格式 | 🟡 中 | 统一为 `JSONMap` 格式 | P0 |
| D2 | 两套 BL 实现并存（optimizer vs alpha_view_service） | 🔴 高 | 统一类型或定义清晰边界契约 | P0 |
| D3 | Go 测试因网络超时 `[setup failed]` 大面积失败 | 🔴 高 | 配置 GOPROXY 或 vendor 依赖 | P0 |
| D4 | 前端组件测试覆盖率 0% | 🟡 中 | 为核心页面添加 vitest 测试 | P2 |
| D5 | 文档版本号分散不一致 | 🟢 低 | 统一版本管理机制 | P1 |

**D2 深入分析**：

项目中存在两套 Black-Litterman 实现：

```go
// 实现 A: services/optimization/black_litterman.go（纯计算）
type BlackLittermanOptimizer struct { ... }
// 使用 map[string]float64，纯数学计算，无数据库交互

// 实现 B: services/alpha_view_service.go（GORM 服务）
type BlackLittermanService struct { ... }
// 使用 models.JSONMap，有 DB 持久化，支持 UPSERT
```

**修复选项**:
- **选项 1（推荐）**: 保持分离，明确契约——A 用于纯计算场景，B 用于持久化+业务流程。添加跨实现一致性测试。
- **选项 2**: 统一到 B，让 optimization 包调用 alpha_view_service。
- **选项 3**: 提取共享核心到 `internal/blcore`，两者都调用。

### 4.4 质量门禁矩阵

| 门禁 | 当前 | 目标 | 工具 | 执行时机 |
|------|------|------|------|----------|
| Go 编译 | ✅ | 保持 | `go build ./...` | pre-push |
| Go 格式化 | ✅ | 保持 | `gofmt` + `goimports` | pre-commit |
| TypeScript 类型检查 | ✅ | 保持 | `tsc --noEmit` | pre-commit |
| ESLint | ✅ | 保持 | `eslint` | pre-commit |

| 集成测试 | 部分 | 全部核心端点 | `httptest` + `gin.TestMode` | CI |
| 性能基准 | ❌ 无 | P95 < 200ms | k6/hey | CI（每日） |

## 5. 与现有规划的关系

### 5.1 与 EVOLUTION_ROADMAP_2026 的对齐

本设计直接对应路线图中的 **"方向一：质量提升 (Quality First)"** 章节，将其从概念细化为本可执行的分层计划。

### 5.2 与 Design Doc 003 的关系

003 文档定义了"向专业金融分析工具演进"的愿景（方案 C）。本设计（方案 B）是达成该愿景的**必要前置阶段**——不先稳固基础，平台化架构只会放大技术债务。

### 5.3 与进行中 Phase 的关系

- **Phase 4 (Analytics)**: 已采用 TDD，与本设计的 P0 策略完全一致，无需调整
- **未来 Phase**: 质量提升完成后，Phase 5+ 可以更自信地推进

## 6. 风险与缓解

| 风险 | 可能性 | 影响 | 缓解措施 |
|------|--------|------|----------|
| 团队对 TDD 文化不适应 | 中 | 中 | 从 P0 核心模块开始小范围试点，逐步推广 |
| 测试编写耗时影响进度 | 中 | 中 | 设定合理的覆盖率目标（非盲目追求100%） |
| D2 双 BL 实现统一引发回归 | 低 | 高 | 先加集成测试保护，再重构 |
| 前端测试环境搭建成本 | 中 | 低 | 使用 Vite 内置 vitest，配置简单 |
